# StudyDesk

Учебна работна среда, която живее изцяло в браузъра ти. Отваряш PDF учебник или започваш
на празна дъска, решаваш директно върху страницата, изрязваш задача и я пренасяш другаде,
правиш флашкарти от нея, планираш контролните и следиш колко време си учил по кой предмет.
Отстрани държиш калкулатор, периодична таблица или графика, а върху листа слагаш линийка,
транспортир и триъгълник, по които мастилото върви идеално право.

Всичко се пази **на устройството** (IndexedDB) и работи офлайн. Ако искаш същата библиотека
и на телефона, добавяш профил и тя се синхронизира — по избор, през твоя собствена безплатна
Supabase база. Без профил приложението работи точно толкова добре; тогава архивът в един файл
е начинът да преместиш всичко.

```bash
npm install
npm run dev      # http://localhost:5180
npm run build    # готово за качване съдържимо на dist/
```

| Слой | Избор | Защо |

| PDF рендер | **pdf.js** (`pdfjs-dist`) | Единствената зряла browser библиотека, която рендерира PDF вярно; дава и текстов слой за търсене, и `viewport.convertToPdfPoint` за точна координатна трансформация при експорт. |

| Стил | Tailwind CSS v4 + CSS променливи | Темите са само смяна на променливи; цветът на предмета минава през същия механизъм. |
| State | Zustand | Минимален, без boilerplate, позволява четене на състоянието извън React (нужно е в pointer handler-ите, където не искаме re-render). |
| Storage | IndexedDB през `idb` | Единственото browser хранилище, което държи стотици мегабайти PDF-и. |
| Експорт | `pdf-lib` | Пише анотациите като истински векторни обекти. |
| Архив | **собствен контейнерен формат** | Zip библиотека щеше да добави тегло само за да опакова блобове, които и без това не се компресират. |
| Офлайн | **ръчно написан service worker** | 40 реда вършат работата на цял plugin: HTML network-first, всичко останало cache-first. |
| Профил и sync | **Supabase** (Postgres + Auth + Storage), зареден лениво | Единственият безплатен план, който дава едновременно вход с имейл, релационна база и файлово хранилище, без сървър за поддържане. ### Предметът като ос

`Subject` е единственият междумодулен ключ: `DocumentMeta`, `FlashCard`, `PlannerItem`,
`Grade`, `ClassSlot` и `FocusSession` носят `subjectId`. Затова цветът на предмета се
появява навсякъде без специален код, а въпросът „колко учих по математика“ е един
`filter`, а не отделна таблица.

Учебната сесия си взима предмета сама — от документа, който е бил отворен, или от
задачата, върху която е фокусиран таймерът. Никой не въвежда нищо ръчно.

### `PageSource` — учебникът и дъската са едно и също нещо

```ts
interface PageSource {
  pageCount; defaultSize;
  getSize(page); knownSize(page); viewport(page, scale);
  render(key, page, canvas, scale); cancel(key);
  getText(page); findOnPage(page, query);
}
```

`PdfSession` го изпълнява чрез pdf.js, `BoardSession` рисува хартия. Затова
виртуализацията, писането, гумата, undo/redo, autosave, thumbnail-ите, търсенето,
тъмната тема и експортът важат за дъската **без нито ред специален код**.

### PDF слой + Annotation слой

```
┌─ page-shell ─────────────────────────┐
│ canvas.pdf-canvas   ← PDF или хартия │  само за четене
│ canvas.ink-canvas   ← мои            │  всички записани анотации
│ canvas.live-canvas  ← draft          │  само текущият незавършен щрих
└──────────────────────────────────────┘
```

**Live слоят е причината писането да е плавно.** По време на щрих не се пипа state-ът и
не се прерисува целият ink слой — рисува се само текущата линия върху празен canvas
(с `getCoalescedEvents()` за пълната честота на стилуса).

### Координатна система

Анотациите се пазят в **page space**: PDF точки при scale 1, начало горе вляво. Не зависят
от zoom, от device pixel ratio и от размера на прозореца. Експортът минава през
`viewport.convertToPdfPoint`, което е коректно и при завъртяни страници и при
CropBox ≠ MediaBox; дъската има същия метод — просто `[x, height − y]`.

### Запазване (autosave)

Всяка промяна минава през един `commit(op)`:

```ts
interface AnnotationOp { added: Annotation[]; removed: Annotation[]; label?: string }
```

Преместване или смяна на цвят = „старите излизат, новите влизат“. Затова undo/redo е един
код: обръщаш `added` и `removed`. Непрекъснатите жестове носят общ `label` и се сливат в
едно undo стъпало. Commit-ът пуска debounce от 600 ms, който записва партидата в **една
IndexedDB транзакция**; при скриване на таба и при `⌘S` записът е незабавен.

### Производителност при 500+ страници

Контейнерът има височината на целия документ, но canvas-и има само за видимите страници
(±1) плюс празни бели „черупки“ (±6). Тест с 420 страници: 17 DOM елемента, 5 рендерирани
canvas-а, ~15 MB heap, отваряне за 170 ms.

## Дъска за писане

Дъската е документ с `kind: 'board'`, чиито страници са **рецепта за хартия**, а не файл.

**Хартии:** празна, редове, широки редове, квадратчета 5/10 мм, точки, милиметрова с оси,
нотна, Cornell. Сменя се по всяко време — за цялата дъска или само за една страница.

**Тетрадка** (отделни листа A4/A5/Letter, добавяш/дублираш/местиш/триеш) или **свитък**
(един лист, който порасва сам, щом мастилото се доближи до дъното).

Хартията се описва **като геометрия**, не като картинка: един и същ списък линии се рисува
и на екрана, и в експортирания PDF, затова принтираната тетрадка е с идеални вектори.

## Изрезка, флашкарти, архив

**Ножичката (`C`)** очертава правоъгълник, страницата се рендерира наново при висока
резолюция и се изрязва точно този правоъгълник. После: на дъска (ляга под написаното),
флашкарта, клипборд или PNG.

**Флашкартите** са въпрос/отговор или *image occlusion* — влачиш правоъгълници върху схема
и всеки става отделна карта. Планирането е SM-2; всеки бутон показва къде ще прати картата.
Картите **надживяват документа**, от който са изрязани.

**Тестето е самостоятелно нещо.** По-рано тесте беше просто низ, повторен върху всяка карта —
затова празно тесте изчезваше в мига, в който го направиш, и не можеше да бъде избрано за
следващата карта. Сега имената живеят в `meta.decks`, преживяват празнотата и се избират от
падащо меню (с ред „Ново тесте…“ най-отдолу), а не се преписват на ръка. Тестето се
преименува — картите го следват — и се маха със или без картите вътре.

**Архивът** е един самоописващ се файл:

```
"SPDFBAK1" | uint32 дължина на манифеста | манифест JSON | блобове един след друг
```

Четенето минава през `File.slice`, така че библиотека от 2 GB се възстановява, без нито
веднъж да се държи цялата в паметта.

## Инструменти настрани

Докато решаваш, ти трябват неща, които не са част от листа: калкулатор, периодична
таблица, преобразуване на единици. Досега това означаваше друг раздел на браузъра — и
прекъсната мисъл. Сега те са прозорци до страницата.

| Инструмент | Какво прави |
| --- | --- |
| **Калкулатор** | Научен, с градуси/радиани, скоби, `√`, `!`, `π`, история, която можеш да кликнеш обратно, и жив резултат още докато пишеш израза. |
| **Периодична таблица** | Всичките 118 елемента с маса, електроотрицателност, точки на топене и кипене и електронна конфигурация; оцветяване по групи, по агрегатно състояние или по електроотрицателност. Работи офлайн. |
| **ptable.com** | Оригиналната таблица, вградена като рамка — за когато ти трябва точно тя. Иска интернет. |
| **Мерни единици** | Единайсет семейства; освен исканата стойност показва и всички останали единици наведнъж. |
| **Графика на функция** | До четири функции, влачене и мащабиране, отчитане на стойността под курсора. |
| **Формули** | Алгебра, геометрия, тригонометрия, производни и интеграли, механика, електричество, химия — с копиране. |
| **Триъгълник** | Решава по три известни елемента (SSS, SAS, ASA, AAS) и честно казва, когато SSA има две решения. Чертае го в мащаб. |
| **Бележник** | Черновата, която не бива да остава върху страницата. |

### Свободен или залепен

Всеки прозорец е или **свободен** (плува над всичко), или **закачен** за един от четирите
ръба. Разликата не е козметична: закаченият панел взима истинска ширина от документа, така че
„решавам вляво, калкулаторът е вдясно“ е реален разделен екран, а не кутия върху работата.

Влачиш лентата с името към ръба — появява се очертанието на мястото; пускаш и панелът остава
там. Границата се дърпа. Влачиш обратно навътре и панелът пак плува.

Прозорците се отварят и извън документ (от иконата в горната лента), но там няма какво да
разделят, затова остават свободни.

**Инструментите се зареждат поотделно.** Само данните за периодичната таблица са десетки
килобайта; който отваря единствено калкулатора, не бива да ги тегли. Затова всеки инструмент е
собствен chunk.

**Състоянието им преживява местенето.** Преместването от „свободно“ към „закачено“ е друго
място в React дървото, тоест компонентът се размонтира. Наполовина написан израз, който
изчезва, защото си преместил панела, не е приемлив компромис — затова черновото състояние
живее в `panelState`, извън компонента.

## Геометрични инструменти

Линийка, триъгълник (45·45 или 30·60), транспортир и пергел — върху екрана, не върху листа.

Това е нарочно. Линийката е физически предмет **върху** работата: не бива да се смалява,
когато намалиш мащаба, и една линийка трябва да служи на всички страници, през които
превърташ. Затова инструментите живеят в екранни координати, а прилепването се случва в
`useDrawing`, преди точката изобщо да бъде превърната в координата на страницата.

### Прилепването е „лепкаво“

Истинската линийка не пуска писалката да избяга по средата на линията: щом върхът опре в ръба,
той остава там, докато не вдигнеш ръка. Затова първата точка, която влезе в обхват, заключва
целия жест към този ръб, а всичко след нея се проектира върху него.

Разликата е между „почти права линия“ и права линия.

```
findSnapTarget(x, y, area)   →  кой ръб, ако изобщо някой
applySnapTarget(t, x, y)     →  проекция върху вече избрания
```

Всеки инструмент дава своите ръбове: линийката — двата си дълги ръба; триъгълникът — трите си
страни; транспортирът — основата и дъгата си; пергелът — окръжността, която описва. Пергелът
има и бутон, който начертава цялата окръжност наведнъж, върху страницата под центъра си.

### Мрежа върху екрана

Отделно от инструментите: квадрати, точки, изометрия (0° / 60° / 120°) или ъглова роза с
избираема стъпка. Мрежата може и да води мастилото — по-слабо от инструмент, но върху цялата
страница.

Начертана е с CSS градиенти, а не със SVG или canvas: браузърът пререндерира градиент
безплатно при превъртане, а мрежата така или иначе трябва да стои закована за екрана, не за
хартията.

## Профил и синхронизация между устройства

По подразбиране няма профил и нищо не напуска устройството. Профилът добавя точно едно нещо:
**същата библиотека и на телефона**.

### Как е устроено

Всеки запис вече е плосък JSON обект с `updatedAt`, затова сливането на две устройства не иска
никаква логика на сървъра — по-новият запис печели, и в двете посоки. Цялата база е една
таблица:

```sql
records (user_id, kind, id, doc_id, updated_at, deleted, data jsonb)
```

`kind` е локалното хранилище, от което идва редът (`documents`, `annotations`, `cards`, …).
Row-level security заключва всеки ред за собственика му, така че никой не може да види чужди
бележки — дори публичният ключ да е у него.

**Изтриването пътува като запис**, не като липса. Ред, който просто е изчезнал, е неразличим
от ред, който другото устройство още не е виждало — и щеше да бъде възкресен при следващото
качване. Затова всяко локално изтриване оставя *tombstone*, който се качва и после се изчиства.

Изтрит учебник отнася бележките, отметките, картинките и файла си с една заявка по `doc_id`,
вместо с хиляди отделни надгробни камъка.

**Файловете не са в таблицата.** PDF-ите и изрязаните картинки живеят в Storage, в папка на
името на потребителя, и се обявяват с малък запис `blobs`. Картинките се теглят веднага —
малки са. PDF се тегли чак когато отвориш документа. Затова влизането в профил на нов телефон
трае секунди, а не докато се свали всяка книга.

### Настройка (веднъж, около пет минути)

1. Направи безплатен проект в [supabase.com](https://supabase.com/dashboard) (регион Frankfurt).
2. **SQL Editor → New query** → постави [`supabase/schema.sql`](supabase/schema.sql) → **Run**.
   Същият скрипт стои и в приложението, с бутон за копиране. Накрая той сам се проверява —
   двата реда трябва да покажат `1`.
3. **Storage → New bucket** → име `library`, оставено **private**. На някои проекти SQL редът
   за кофата няма права и трябва да се направи оттук.
4. **Authentication → Sign In / Providers → Email** → изключи **Confirm email**, ако искаш
   регистрацията да влиза веднага. Иначе Supabase праща писмо и до потвърждаване няма сесия —
   тоест „регистрирах се, а пише че не съм влязъл“.
5. **Project Settings → API** → копирай адреса и **publishable** ключа.
6. В приложението: аватарът → **Влез в профил** → постави двете стойности.

Стойностите могат да дойдат и от `.env`, ако публикуваш за няколко души наведнъж. Приемат се и
двата начина на изписване — включително точно този, който Supabase дава за копиране:

```bash
SUPABASE_URL=https://xxxx.supabase.co
SUPABASE_PUBLISHABLE_KEY=sb_publishable_…
# или
VITE_SUPABASE_URL=…
VITE_SUPABASE_ANON_KEY=…
```

Vite подава на браузъра само променливи с префикс `VITE_`, затова `vite.config.ts` превежда
имената на Supabase — иначе поставеният `.env` мълчаливо не прави нищо. **След промяна в `.env`
рестартирай `npm run dev`.** Виж [`.env.example`](.env.example).

> Адресът и publishable ключът са публични по замисъл — сами по себе си не дават достъп до
> нищо. Защитата е в правилата на базата, не в скриването на ключа.
>
> **`SUPABASE_SECRET_KEY` никога не влиза тук.** Това е браузърно приложение: всичко, което
> получи, се чете от всеки, който отвори страницата. Приложението отказва такъв ключ, ако бъде
> поставен по погрешка. По същата причина `@supabase/server` не ти трябва — няма бекенд.

### Когато нещо не работи

На екрана за вход има **„Провери връзката“**. Минава по една стъпка наведнъж — настройка,
достъпен ли е проектът, влязъл ли си, има ли таблица `records`, има ли кофа `library`, иска ли
се потвърждение по имейл — и за всяка казва какво да натиснеш.

Кофата се проверява чак след влизане, и то с истинско качване на един байт: Supabase отговаря
`[]` с код 200 на изброяване в кофа, която изобщо не съществува, така че по-евтината проверка
винаги би излизала зелена.

Липсваща кофа вече **не проваля синхронизацията** — бележките, картите и задачите минават, а
файловете се пропускат с предупреждение.

### Входната врата

Когато сглобката носи база, приложението **отваря на „Влез / Регистрация“** — не на въпрос за
име. „Продължи без профил“ се помни, така че вратата не се показва пак; влизането или излизането
я връща.

Ако сглобката няма база, тази стъпка изобщо не се появява: няма в какво да се влиза, а
настройването на базата е работа на този, който публикува сайта, не на ученика пред него.
Затова екранът „Свържи база“ живее зад профилното меню, а не пред посетителите.

### Кога се синхронизира

При влизане, на всеки 5 минути, при затваряне на таба и когато натиснеш „Синхронизирай“.
Може да се изключи. Всяка стъпка си казва какво прави и колко записа са минали.

## Публикуване

Приложението е статично: `npm run build` прави папка `dist/`, която е просто файлове.
Няма база данни, няма backend, няма какво да се поддържа.

### Изисквания към хостинга

1. **HTTPS.** Без него не работят service worker-ът (офлайн), Wake Lock (екранът да не
   заспива) и трайното съхранение. `localhost` е изключение и работи без сертификат.
2. **SPA пренасочване** — всички пътища да връщат `index.html`.
3 . Нищо друго. Никакви environment променливи, никакви ключове.

### Най-бързият вариант: Netlify Drop (2 минути, безплатно)

```bash
npm run build
```

Отвори <https://app.netlify.com/drop> и **влачи папката `dist`** в браузъра. Получаваш
адрес от рода на `https://study-desk-abc123.netlify.app` — прати го на когото искаш.

За да не се чупи презареждането на подстраница, сложи до `dist/` файл `_redirects`:

```
/*  /index.html  200
```

Най-лесно: направи `public/_redirects` със същото съдържание — Vite го копира при всеки build.

### Vercel или Cloudflare Pages (свързани с Git, обновяват се сами)

```bash
npm i -g vercel && vercel        # следва въпросите; build: npm run build, output: dist
```

Или в Cloudflare Pages → Create project → Connect to Git:
* Build command: `npm run build`
* Build output directory: `dist`

И двете правят SPA пренасочването сами за Vite проекти.

### GitHub Pages

Pages сервира от подпапка, затова трябва базов път. Във `vite.config.ts`:

```ts
export default defineConfig({
  base: '/име-на-хранилището/',
  // …
});
```

и в `public/manifest.webmanifest` смени `"start_url"` и `"scope"` на същия път. После:

```bash
npm run build
npx gh-pages -d dist
```

### Собствен сървър (nginx)

```nginx
server {
  listen 443 ssl;
  server_name study.example.com;
  root /var/www/studydesk;

  # SPA: всеки път връща index.html
  location / { try_files $uri $uri/ /index.html; }

  # Хешираните файлове никога не се променят
  location /assets/ { expires 1y; add_header Cache-Control "public, immutable"; }

  # …но service worker-ът и index.html трябва да се проверяват всеки път,
  # иначе обновяването не стига до хората
  location = /sw.js      { add_header Cache-Control "no-cache"; }
  location = /index.html { add_header Cache-Control "no-cache"; }
}
```

Сертификат: `sudo certbot --nginx -d study.example.com`.

### Само в домашната мрежа (без интернет)

```bash
npm run build
npx serve dist -l 8080
```

После от телефон или таблет в същия WiFi: `http://<ip-на-компютъра>:8080`.
Забележка: по HTTP (не HTTPS) офлайн режимът и Wake Lock няма да работят.

### Профил за няколко устройства

Ако публикуваш за себе си и искаш библиотеката да те следва между компютър и телефон, виж
[Профил и синхронизация](#профил-и-синхронизация-между-устройства).

**Най-простият начин: [`public/cloud.json`](public/cloud.json).**

```json
{
  "url": "https://xxxx.supabase.co",
  "anonKey": "sb_publishable_…"
}
```

Файлът се копира в `dist` както си е и се чете при стартиране на приложението. Затова работи и
при влачене на папката, и при деплой от Git, и смяната на проект не иска ново сглобяване.

Това не е компромис със сигурността: и двете стойности така или иначе стоят в JavaScript-а на
всеки сайт със Supabase — четат се с Ctrl+U. Защитата е в row-level security. (Тайният ключ е
друго нещо и няма работа тук.)

**Защо не само `.env`:** `.env` правилно не е в хранилището, затова хост, който строи от Git,
произвежда сглобка без никакви ключове — жив сайт, който кара посетителите си да свързват база.
Точно това е капанът, който `cloud.json` премахва.

Build-ът казва кое носи връзката:

```
StudyDesk · облак: от public/cloud.json → https://xxxx.supabase.co
```

Ако пише `НЯМА`, качената папка ще работи само локално и няма да показва вход.

**Другите два начина** остават и имат предимство пред файла: `.env` при локално сглобяване, и
Site settings → Environment variables (`SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`) при
Netlify/Vercel, свързани с Git.

И още едно: за да работят връзките от писмата за потвърждение и за нова парола, адресът на сайта
трябва да е разрешен — Supabase → **Authentication → URL Configuration** → добави го в
**Site URL** и в **Redirect URLs**. Иначе писмото връща на `localhost`.

### Ограничаване до малък кръг хора

Приложението няма собствени пароли — няма сървър, който да ги проверява. Ограничението
се прави на ниво хостинг:

* **Netlify** → Site settings → Access control → *Password protection* (една обща парола).
* **Cloudflare Access** (безплатно до 50 души) → пускаш само конкретни имейли, влизането
  е с код по пощата. Най-доброто съотношение сигурност/усилие.
* **nginx Basic auth** за собствен сървър:
  ```bash
  sudo htpasswd -c /etc/nginx/.htpasswd ivan
  ```
  ```nginx
  location / {
    auth_basic "StudyDesk";
    auth_basic_user_file /etc/nginx/.htpasswd;
    try_files $uri $uri/ /index.html;
  }
  ```
* **Нелистван адрес** — най-простото. Няма индексиране, адресът се знае само от вас.
  Достатъчно е за клас или приятелски кръг; не е защита срещу някой, който наистина търси.

Важно: **всеки, който отвори адреса, си има собствени данни.** Няма как един ученик да
види бележките на друг — те дори не напускат неговия браузър. Дори с включен профил всеки
ред в базата е заключен за собственика си. Обратното също е вярно: няма как да си споделите
тетрадка, освен като си пратите архивния файл.

### Инсталиране като приложение

След като е публикувано по HTTPS:

* **iPhone/iPad (Safari):** Сподели → „Към началния екран“.
* **Android (Chrome):** менюто ⋮ → „Инсталиране на приложението“.
* **Windows/Mac (Chrome/Edge):** иконката за инсталиране вдясно в адресната лента.

Отваря се на цял екран, без адресна лента, с икона на началния екран, и работи офлайн.

### Обновяване

Качваш ново `dist/` и хората го получават при следващото зареждане (HTML е network-first).
Ако си сменил нещо в самия service worker, вдигни `VERSION` в [`public/sw.js`](public/sw.js) —
иначе старият кеш остава.

### Преди да качиш: провери размера

`dist/` е около **6,7 MB** на диска, но при първо зареждане се тегли много по-малко:

| Папка | Размер | Кога се тегли |
| --- | --- | --- |
| `assets/` | ≈2,5 MB (≈173 KB gzip при първо зареждане) | кодът — веднага |
| `assets/supabase*` | 218 KB (≈58 KB gzip) | само ако си настроил профил |
| `assets/PeriodicTable*`, `Calculator*` … | по 2–16 KB | само при отваряне на съответния инструмент |
| `cmaps/` | 1,6 MB | само при PDF с китайски/японски/корейски текст |
| `wasm/` | 1,6 MB | само при PDF с JBIG2/JPEG2000 изображения |
| `standard_fonts/` | 1,0 MB | само при PDF без вградени шрифтове |

Тоест обикновено зареждане е под 500 KB. Ако хостингът ти брои строго трафика или искаш
по-леко хранилище, `public/cmaps/` може да се изреже — тогава просто няма да се показва
текст в PDF-и на азиатски езици.

## Защо sync-ът се получи толкова малък

Целият достъп до данни минава през интерфейса `StudyRepository`
(`src/services/storageService.ts`), а всеки запис е плосък JSON обект с `updatedAt`. Затова
синхронизацията не изисква нито ред промяна в UI-я или в store-овете: тя е още три метода на
същия интерфейс (`listRecords`, `putRecords`, `dropRecords`) плюс един двигател, който ги
върти в двете посоки.
